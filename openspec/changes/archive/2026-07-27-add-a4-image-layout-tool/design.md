## Context

当前仓库已包含浏览器端图片排版工具，本次修订在保留既有上传、3x3 排序、裁剪、预览和 PNG 下载流程的基础上，规范前端目录分层，并加入页面边距与图片间距设置。图片具有较高隐私性且文件通常较大，因此继续避免服务端传输和存储。

主要约束包括：A4 竖版输出固定为 2480 x 3508 像素；浏览器需要同时处理九张原始图片和高分辨率画布；鼠标与触摸设备都需要可完成排序和图片调整；屏幕预览必须与最终输出使用相同的几何计算。

## Goals / Non-Goals

**Goals:**

- 提供清晰、响应式的上传、排序、图片调整、预览和下载流程。
- 生成固定 3x3、A4 竖版、300 DPI 对应像素尺寸的 PNG。
- 让预览和导出保持一致，包括图片顺序、裁剪、空位、边距和间距。
- 默认使用 0 mm 页面边距和 0 mm 图片间距铺满 A4，并允许用户在受控范围内调整两个参数。
- 建立明确的页面、组件、接口、状态、工具、配置、资源和样式目录边界。
- 在浏览器本地处理图片，并妥善管理高分辨率图片带来的内存压力。
- 为关键布局计算和用户工作流提供自动化测试。

**Non-Goals:**

- 不提供账号、云存储、跨设备同步或服务端图片处理。
- 不支持自由数量的行列、横版 A4、其他纸张尺寸或多页排版。
- 不在首版导出 PDF、JPEG 或专业印刷出血标记。
- 不提供完整图片编辑功能，例如滤镜、旋转、抠图或色彩校正。

## Decisions

### 使用 Vue 3、TypeScript、Vite、Pinia 和 Element Plus 构建单页应用

应用使用 Vue 3 Composition API 组织上传、网格编辑、图片裁剪和 A4 预览组件，使用 TypeScript 约束图片条目、变换参数和布局几何数据，使用 Vite 提供开发与构建基础。Pinia 作为编辑器的单一状态源，集中管理九个格位、图片元数据、裁剪参数、编辑版本和生成状态，使排序、预览失效与资源清理行为可预测并易于测试。Element Plus 提供上传入口、按钮、滑块、对话框、提示和加载状态等基础交互组件，版面网格与 A4 画布仍使用领域专用组件实现。

备选方案包括 React 或仅使用原生 HTML、CSS 和 JavaScript。React 与指定技术栈不一致；原生方案虽然依赖更少，但随着拖拽、触控和图片变换状态增加，事件与状态同步会更难维护。

### 按职责组织前端目录与依赖方向

应用采用以下目录约束：

- `src/pages/` 放置页面级组件，A4 排版工作区由页面组件组合各领域组件。
- `src/components/` 只放置可复用组件，不直接发起请求或持有页面级业务流程。
- `src/api/` 作为唯一接口访问边界；当前应用没有服务端请求，但保留统一入口，未来组件不得直接编写请求逻辑。
- `src/store/` 放置 Pinia 跨页面状态和 action，替代现有 `src/stores/` 路径。
- `src/utils/` 放置不依赖 Vue 组件状态的纯工具函数，包括布局、裁剪、图片解码、Canvas 渲染、格式化、缓存和 URL 处理。
- `src/config/index.ts` 收口 A4 尺寸、DPI、设置范围、文件限制等项目级配置。
- `src/assets/` 放置由构建工具处理的图片、字体和其他资源。
- `src/public/` 放置原样复制的静态公共资源，并通过 Vite `publicDir` 指向该目录。
- `src/style/` 放置应用级全局样式；`src/assets/css/` 放置主题样式及需要时启用的 Tailwind 入口。

依赖方向保持为 `pages -> components/store/api -> utils/config`。`api` 可以依赖 `utils/config`，但组件不得绕过 `api` 直接编写网络请求，纯工具函数不得依赖页面或组件。

### 图片数据只保存在当前浏览器会话

Pinia 编辑器 store 为每个图片条目保存稳定 ID、原始 `File`、对象 URL、解码后的自然尺寸，以及归一化的缩放和偏移参数；同时保存统一页面边距和统一图片间距。删除图片和卸载页面时释放对象 URL。页面刷新后状态可以丢失，不为 store 引入持久化插件。

备选方案是将图片写入 IndexedDB，但这会增加存储配额、清理和隐私行为的复杂度，首版没有跨刷新恢复需求。

### 使用成熟拖拽库实现排序

选择兼容 Vue 3 且基于 SortableJS 的成熟拖拽排序库，例如 `vue-draggable-plus`，处理鼠标和触摸排序。排序结束后通过 Pinia action 更新格位顺序，图片的缩放与偏移跟随稳定 ID 保留。键盘用户通过 Element Plus 图标按钮或操作菜单执行前移、后移和移动到指定空位，以满足等价操作要求。

备选方案是直接使用 HTML5 Drag and Drop API，但其触摸设备支持不足，需要额外编写大量兼容逻辑；只依赖拖拽库也无法完整覆盖键盘操作，因此仍需显式排序命令。

### 采用“铺满并裁剪”的统一图片适配模型

图片进入格子后以 cover 规则计算最小铺满缩放，初始居中。用户可以在允许范围内继续缩放和移动图片，系统限制偏移，确保格子内不会暴露空白。编辑器、预览和导出使用同一组归一化参数。

备选方案是 contain 完整显示图片，但不同宽高比会产生不一致留白，不符合紧凑打印排版目标。

### 集中定义 A4 布局几何参数

导出画布固定为 2480 x 3508 像素，对应 A4 竖版在 300 DPI 下的常用栅格尺寸。页面边距默认 0 mm，可在 0 至 30 mm 范围内按 1 mm 调整；图片间距默认 0 mm，可在 0 至 20 mm 范围内按 1 mm 调整。两个值都是同时作用于所有方向的统一参数。

A4 尺寸、DPI、默认值与允许范围收口到 `src/config/index.ts`。纯布局函数接收当前边距和间距，将毫米换算为像素并计算九个格子矩形。尺寸取整产生的余数由最后一行或最后一列吸收，确保边界准确。Pinia action 对设置值进行范围约束，并在值变化时递增编辑版本，使旧预览和下载结果失效。

备选方案是分别控制上下左右边距和水平垂直间距，但会显著增加首版控制复杂度；统一参数足以满足铺满页面和常见留白需求。

### 预览与导出共享渲染模型

界面中的 A4 预览按比例缩放同一组页面和格子矩形。导出时创建离屏 Canvas，以白色填充背景，直接从解码后的原始图片按裁剪参数绘制，而不是截取 DOM 或放大屏幕预览。生成成功后通过 Blob URL 触发 PNG 下载，并及时释放临时资源。

备选方案是使用 DOM 截图库，但它可能受 CSS、设备像素比和浏览器渲染差异影响，难以稳定得到准确的 2480 x 3508 输出。

### 将“生成预览”作为显式确认步骤

编辑区持续提供轻量的版面缩略视图；用户点击“生成预览”后进入完整 A4 确认状态。任何排序、删除或图片变换都会将已生成结果标记为过期，下载前必须重新生成，从而避免下载与当前编辑状态不一致的内容。

确认弹窗中的下载开始后立即关闭弹窗并返回编辑界面，避免用户误以为仍需重复确认。点击某个空格位发起上传时，页面将该格位索引传入 store，首张成功解码的图片优先进入该格位；其余入口仍按第一个可用格位添加。

## Risks / Trade-offs

- [九张超高分辨率图片和导出 Canvas 可能造成内存峰值] -> 限制支持的文件类型与单文件大小，按需解码，释放对象 URL、Canvas 和下载 Blob，并在生成期间显示忙碌状态。
- [Canvas 可能因异常或受污染的图片源无法导出] -> 只接受用户本地选择的 File，并捕获解码及导出错误，向用户提供可恢复的错误提示。
- [浏览器拖拽和手势可能与图片平移冲突] -> 将排序手柄与图片调整区域分离，并为触摸交互设置明确的手势策略。
- [PNG 像素尺寸不能在所有打印软件中强制物理 A4 尺寸] -> 明确输出为 2480 x 3508，并在界面中标注按 A4、100% 或适合页面打印；未来可增加带物理页面定义的 PDF 导出。
- [边距或间距过大可能让图片格位过小] -> 在 Pinia action 和输入控件中限制允许范围，并让预览即时反映结果。

## Migration Plan

不涉及持久化数据迁移。实施时先建立目标目录，再逐步移动页面、store、样式与配置文件并修正导入路径；随后参数化布局与渲染函数，最后加入设置控件和测试。部署仍使用静态构建产物，回滚只需恢复上一版本构建，不涉及用户数据转换。

## Open Questions
